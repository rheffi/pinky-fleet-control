# Pinky Fleet Control — 프로젝트 메인

갱신: 2026-09-16

**샘플 관제 구현·검증 완료(F1~F6).** [관제 화면](http://127.0.0.1:8080/) · [환경 확인](http://127.0.0.1:8080/environment) · [상태 API](http://127.0.0.1:8080/api/health)

기존 Docker 4개 서비스에 sample profile의 샘플 실행기를 추가했다. 로봇 3대 상태·목표·경로·작업·이벤트를 샘플로 표시하며, 실제 로봇과 알고리즘은 아직 연결하지 않았다.

## 1. 목표와 진행 원칙

실제 PinkyPro 3대가 하나의 공통 지도에서 지정된 목적지로 이동하고, 공용 통로에서 대기·통과 순서를 조정하는 모습을 Laravel + Vue 관제 화면으로 시연한다.

**진행 순서: 현재 Windows 노트북에서 Docker 개발 → Ubuntu 관제 노트북에 조기 배포 → 실물 한 대 연결 → 두 대·세 대 통합 → 인터넷 없이 시연.**

이 README가 전체 계획과 진행 상황의 기준이다. 세부 문서를 한꺼번에 만들지 않는다. 다음 작업을 시작할 때 해당 단계의 문서 하나를 작성하고, 계획·실행·검증 결과를 같은 문서에 누적한다. 이전에 작성한 상세 문서는 이전 초안이며, 현재 결정이나 완료 증거로 자동 적용하지 않는다.

## 2. 확정한 구성

| 항목 | 결정 |

## 3. 시스템 구조

```text

  Docker: Laravel + Vue 개발·빌드 + MySQL
  샘플 데이터로 API·관제 화면 확인
                 │

  팀원 알고리즘 연결 / 실제 로봇 실행 관리
                 │
        공유기 내부망 / HTTP API
       ┌─────────┼─────────┐
     eed0       648d      62b2
   Domain 35  Domain 30  Domain 40
     각 로봇: 위치 추정·Nav2·모터 제어
```

알고리즘과 실행 관리 프로그램의 프로세스 구성·배치 위치는 담당자와 합의한다. ROS2가 필요한 부분은 담당자가 검증한 환경에서 먼저 연결한다. Laravel은 작업·명령·상태를 관리하며, Vue나 PHP 웹 요청에서 모터 제어 루프를 돌리지 않는다.

## 4. 시연 범위

### 필수 시나리오: 공용 통로를 이용하는 로봇 3대

1. 세 로봇을 지정된 시작 위치에 놓고 공통 지도에서 위치 추정을 확인한다.
2. 관제에서 미리 정한 고정 목적지 시나리오를 선택한다.
3. 로봇별 목적지와 알고리즘의 계획 경로·대기를 표시한다.
4. 실행하면 서로 간섭하지 않는 구간에서 함께 이동한다.
5. 공용 통로에서는 실제 진행 상태를 확인하며 대기·진입·통과를 관리한다.
6. 목적지 도착 결과와 소요 시간·대기·오류 기록을 표시한다.

시작점·목표는 공통 지도 확정 후 고른다. 좁은 통로를 막는 위치에 목적지를 두지 않고, 대기·통과 공간을 확인한다. 구체적인 충돌 처리와 진행 허가 방식은 알고리즘·실행 담당자가 함께 검증한다.

### 최소 관제 기능

- 로봇 3대의 연결 상태, 마지막 상태 수신 시각, 현재 위치.
- 공통 지도, 고정 목적지, 계획 경로와 실제 위치 표시.
- 작업 시작, 전체 정지 요청, 작업 결과 조회.
- 이동·대기·도착·오류 상태와 작업 로그.
- 샘플 모드와 실제 로봇 모드 구분.

추가 범위는 필수 시연 완료 후 시작점·목적지 자동 배정이다. YOLO/OpenCV 기능은 현재 필수 범위에 포함하지 않는다.

## 7. 실제 주행에서 반드시 맞출 사항

- **지도:** 실제 지도 이미지와 YAML의 해상도·원점·방향을 기준으로 한다. 이전 25cm 격자·예시 크기를 실제 벽 좌표로 하드코딩하지 않는다.
- **차체:** 사용자 제공 크기는 약 가로 12cm·깊이 14cm·높이 16cm다. 회전 공간·위치 오차를 포함한 통과 여유는 실측한다.
- **계획과 실행:** CBS 예제의 충돌 없는 계획만으로 실물 충돌 방지가 보장되지는 않는다. Nav2에 최종 목적지만 전달했을 때 경로·대기가 보존되는지 별도 확인한다.
- **속도와 지연:** 이동·회전 시간 차이, 속도 제한, 경로 이탈에 대해 대기·진행 허가·재계획 정책을 정한다.
- **결과:** HTTP 요청 접수와 실제 출발·도착·정지를 구분한다. 상태 값 하나가 false라는 이유로 도착이나 정지를 확정하지 않는다.
- **통신 실패:** 상태가 오래됐거나 연결이 끊기면 다음 구간 진입을 보류하고, 로봇 측 정지·복구 동작을 시험한다. 통신이 끊겼을 때 관제의 정지 요청만으로 멈출 수 있다고 가정하지 않는다.

## 8. 인터넷 없는 현장 배포

공유기 내부 통신에는 인터넷이 필요하지 않다. 장비 간 통신 허용, IP 할당·주소 예약, API 수신 주소, 방화벽·Docker 포트 설정을 확인한다. IP와 포트는 아직 미확정이며, ROS Domain 번호와 구분한다.

배포 순서:

1. 인터넷이 되는 환경에서 Ubuntu·Docker 설치와 필요한 의존성 준비를 마친다.
2. 현재 노트북에서 배포 대상 CPU 구조에 맞는 Linux 이미지를 빌드한다. 앱 의존성과 Vue 빌드 결과를 포함하고 MySQL 등 필요한 이미지도 함께 준비한다.
3. 코드와 설정은 Git으로 공유한다. 오프라인 현장에는 Docker 이미지 파일, Compose 설정, 지도 파일을 USB 또는 내부망으로 전달한다.
4. Ubuntu에서 이미지를 불러오고, 현장 환경변수·DB 볼륨·앱 키·DB 초기화를 설정한다. 이미지 전달은 DB 데이터 백업을 대신하지 않는다.
5. 현장에서는 외부 다운로드 없이 실행되도록 구성한다. 외부 CDN·폰트·클라우드 API 의존성을 제거하고, Gurobi를 계속 쓰면 라이선스의 오프라인 동작을 확인한다.
6. 인터넷을 끊고 재부팅한 뒤 관제 실행·로봇 3대 상태 조회·주행을 검증한다.

개발은 코드 수정이 바로 반영되게 구성하고, 시연은 빌드된 화면과 버전을 고정한 이미지로 실행한다. Wi-Fi 비밀번호·토큰·실제 환경변수는 Git과 문서에 저장하지 않는다.

## 10. 문서 작성과 다음 작업

**샘플 관제 구현·검증을 완료했다.** 다음 단계는 Ubuntu 조기 배포와 실제 로봇 한 대 상태 연결을 위한 배포 구성·인터페이스 확인이다. 공통 지도와 로봇 API 응답을 받아 실제 좌표·목표 연동 범위를 정한다.

검증 중 테스트 DB 격리 오류로 기존 개발 DB의 샘플 작업 이력·환경 확인값이 초기화됐다. 테스트 bootstrap에서 모든 환경변수 출처를 SQLite 메모리 DB로 고정하고, migration 전에 잘못된 DB 연결을 거부하도록 수정했다. 이전 이력은 복구하지 못했으며 이후 새 샘플 데이터로 테스트·재시작 보존을 확인했다. 상세 기록은 02 문서 5.4에 남긴다.

세부 문서는 필요할 때 한 개씩 만들며 아래 순서로 기록한다.

1. 목표와 이번 작업 범위.
2. 확인한 환경·결정 사항·남은 질문.
3. 실행할 작업과 완료 기준.
4. 실제 명령·변경 파일·결과.
5. 검증 결과·미해결 문제·다음 작업.
